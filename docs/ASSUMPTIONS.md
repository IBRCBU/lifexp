# Assumptions and project boundaries

This project is being built as a student-facing mobile application for an academic project. The assumptions below clarify the intended implementation scope and support the phased delivery model.

## General assumptions

1. Firebase is the required backend for authentication, Firestore, FCM, and notification delivery. The project uses FlutterFire configuration generated by the FlutterFire CLI and will not hardcode Firebase credentials into source control.
2. The app is designed primarily for Android-first mobile usage, while preserving compatibility with iOS and web build targets where feasible.
3. A real-world production deployment will require a Firebase project, Firestore rules, and a generated `google-services.json` file for Android, plus `GoogleService-Info.plist` for iOS.
4. The app is built as a single-user mobile experience, but the roles and permissions model is designed for future multi-user verifications and admin workflows.
5. The verification and XP processes are implemented with clear client-side services and Firestore transaction patterns; optional Cloud Functions may be introduced later to harden the server-side rules.

## Role assumptions

- User accounts are created via email/password registration.
- Verifier accounts are linked through a short invite code and can review pending tasks assigned to them.
- Admin accounts are not automatically created during registration; they are assigned manually in Firestore or through a secure admin setup process.
- Self-verification is available only when the user is not linked to a verifier and is intentionally gated behind a configuration flag.

## Gamification assumptions

- XP is awarded only when an approved task is verified.
- The level formula is fixed as `floor(sqrt(totalXP / 100)) + 1`, as requested by the project brief.
- A streak is considered active once per local date when at least one approved task is recorded for that day.
- If a task is approved on the next day after completion, the task still counts for the approval date when the verification is processed; this is documented in the project logic and can be adjusted later if business rules change.

## Notification assumptions

- Local reminders are implemented using `flutter_local_notifications` and are configured under application settings.
- FCM push notifications require a Firebase Cloud Messaging setup and device token registration.
- Notification settings are per-user and stored in the user document or a dedicated profile collection.

## Delivery assumptions

- The repository is iteratively developed in phases; this first phase establishes the project foundation and architecture.
- Screens and services are intentionally structured to support later feature implementation with minimal refactoring but remain placeholder-based in this phase.
- The code is builder-friendly and follows a feature-first architecture to align with the academic project report structure.

This file should be updated as the implementation matures and when real constraints are discovered during later phases.
